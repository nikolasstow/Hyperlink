# agent-console → React Native / Expo — prep notes

## One-sentence idea

A native iOS/Android `agent-console` client built with Expo, sharing the non-UI logic with the existing web client via `last-ts`'s DI patterns, with web staying "somewhat comparable" and native leaning into an iOS-native ("Liquid Glass") look. A Liquid-Glass-style Mac app is a further-out aspiration, explicitly lower priority.

## What's already true of the current code (no work needed here)

`packages/agent-console/src/opencode/` — `client.ts`, `useSessionStream.ts`, `useSessionDetails.ts` — is already plain React hooks + fetch-based SDK calls, with **zero DOM APIs**. This layer is the natural shared core; it doesn't need a refactor to become "reusable," it already is, modulo two real platform seams below.

Everything else (`components/`, `pages/`, `styles.css`, `viewTransition.ts`, `site.tsx`'s `last-ts/Route`+`last-ts/Router` usage) is web-specific and would need a native counterpart, not a port — `View`/`Text`/`StyleSheet` instead of `div`/CSS, a native navigation library instead of `last-ts/History`, no View Transitions API equivalent (RN has its own screen-transition primitives via whichever navigation library is chosen).

## Two real platform seams found (not guessed — grounded in the actual code + current RN ecosystem state)

1. **`client.ts`'s base URL is a web-only trick.** It defaults to the relative path `/opencode`, which only resolves correctly because Vite's dev-server proxy (`vite.config.ts`) forwards it to `127.0.0.1:4096` — same mechanism that fixed the earlier "stuck loading over Tailscale" bug (see git history / README). React Native has no page origin to resolve a relative URL against. A native client needs a real configured base URL — most likely a settings screen persisting it (e.g. `AsyncStorage`/`expo-secure-store`), still pointed at the dev machine over Tailscale for now, since `opencode serve` only binds to loopback and nothing here proxies for native yet.

2. **The OpenCode SDK's streaming isn't `EventSource` — it's `fetch()` + `ReadableStream`, and that matters.** Checked `@opencode-ai/sdk`'s `createSseClient` directly (`dist/gen/core/serverSentEvents.gen.js`): it does `response.body.pipeThrough(new TextDecoderStream()).getReader()`, not the browser `EventSource` global. RN has never had `EventSource` natively, so that specific polyfill gap doesn't apply here. But it is NOT automatically safe: Expo SDK 54 added global `ReadableStream`/`WritableStream`/`TransformStream` + `TextDecoderStream` to the native runtime specifically to support this pattern — and there's a **real, specific regression on record**: [expo/expo#37310](https://github.com/expo/expo/issues/37310), SDK 53, where `expo/fetch` streaming **batched every chunk into one delivered at the very end** instead of arriving incrementally — the backend genuinely streamed (confirmed via curl in that issue), only the client-side delivery was broken. That would silently kill the live "typing" effect this whole chat UI is built around — the response would just jump to fully-formed instead of streaming in. The issue is closed as "outdated" against later SDKs, which is a *weak* positive signal (SDK 54's added stream classes plausibly fixed it), not a confirmation.
   - **This environment cannot verify it further.** No iOS Simulator (`simctl` unavailable) and no Android emulator/`adb` here — I could research the ecosystem but not actually run a device/simulator to confirm real-time chunk delivery. **This is the literal first thing to do** when a real device or simulator is available, before any other native work: `create-expo-app`, point `expo/fetch` at a running `opencode serve`, confirm `event.subscribe()`'s chunks arrive one-by-one (watch them land over a few seconds), not batched at the end. If it's still batching, the live-update design needs a fallback (poll `session.messages()` on an interval, or investigate whether opencode exposes a WebSocket transport) before anything else here is worth building.

3. **Resolved, not just researched: no new `last-ts` code is needed for a working native router.** Checked `last-ts/src/internal/router.ts` and `Router.ts` line by line for DOM dependencies — every `window.*` reference (`Router.ts`'s `popstate` listener, `internal/router.ts`'s `pushState`/`history.back`) is reachable *only* on the `"History"`-tagged engine path, gated by `value._tag !== "History"` / `typeof window === "undefined"` checks. The `"Memory"` engine path — `Memory.service(catalog)` / `Memory.layer` — never touches `window`, `document`, or any browser global at all; it's a plain in-JS pathname/stack tracker. **`Memory.layer` is already usable in React Native today, unmodified**, for the "what should render" half of routing (matching a pathname against the catalog, producing `Route.Match`). This doesn't cover native-feeling screen transitions or deep-link/back-button integration — that's still a real native navigation library's job (Expo Router or React Navigation) — but it means the "prep last-ts for native" question is mostly already answered: reuse `Memory` as-is, don't build a fourth engine, and layer whichever navigation library's screen/transition concerns *on top of* `Memory`-driven matching rather than replacing it.

   Widened the check to the entire package afterward, not just the router files: `grep`'d every `.ts`/`.tsx` under `last-ts/src` for `window.`/`document.`/`localStorage`/`sessionStorage`/`navigator.`/`ReactDOM` — the only other hits are a doc comment (`Memory.ts`'s own "no `window.history`" note), a naming coincidence (`documentCore.ts`'s `Page.document` comment, unrelated to the DOM `document`), and `internal/routerWaku.tsx`'s single reference, itself gated the same `typeof window === "undefined"` way (and Waku-specific — a native app importing `Route`/`Router`/`RouterBuilder`/`Memory` would never reach that file at all). Nothing else in the package touches a browser global anywhere.

## Monorepo integration — researched, looks solid

Expo has shipped real pnpm-workspace monorepo support since SDK 53 (2025), refined in SDK 55: Metro's resolver handles pnpm symlinks natively, EAS Build auto-detects the workspace root from `pnpm-workspace.yaml`. The 2026-recommended stack is pnpm workspaces + Turborepo + Expo SDK 55 + Metro's built-in monorepo support (this repo doesn't have Turborepo — worth deciding whether to adopt it or just add the app as a plain `packages/*` member the way `agent-console` and `last-ts` already are).

Real constraint to plan around: duplicate `react`/`react-native` versions in one monorepo are unsupported and cause runtime errors — would need `pnpm.overrides` in the root `package.json` pinning a single `react` version shared by `agent-console` (web) and the new native package, the same class of constraint `last-ts`'s peer-dependency setup already manages for `react`/`effect`.

## Decisions genuinely left to the owner (not attempted here — multiple valid approaches, real tradeoffs)

- **Where the native app lives**: new `packages/agent-console-native` (sibling to the web one, matching the `last-ts` precedent) vs. splitting a `packages/agent-console-core` (the already-shared `opencode/*` logic) out from both `-web`/`-native` shells vs. something else.
- **Navigation library**: Expo Router (file-based, closer in spirit to how `last-ts`/`RouterBuilder` already works) vs. React Navigation (more mature, more control) — for *screen transitions and native back-button/deep-link wiring* specifically. No longer gates whether `last-ts` routing works at all — see finding 3 above, `Memory.layer` already works unmodified for the matching/DI half.
- **Turborepo adoption** — not currently used anywhere in this repo; the 2026-recommended stack assumes it, but it's a real new tool to bring in, not free.
