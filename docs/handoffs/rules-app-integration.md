# Rules in the app — full docs-parity integration

**Status:** DESIGN — agreed direction, not yet built. Owner-driven.
**Related:** `extensions-sync-and-theming.md` (code highlighting / skills), the skills+rules control-channel discussion (skills doc pending), `docs/standards/`, `.cursor/rules/`, `docs/standards/manifest.json`, `docs/site/` (the web reader we are mirroring).

## Goal

Bring the **web docs-site experience into the app as a first-class feature**, not just OpenCode rule recognition. Rules get their **own app surface** (a menu item below Docs in a repo/workspace), rendered by the **same reader we use for Docs**, **editable** (both the rule and its full standard doc), with an **AI-assisted update** path, **root→repo→folder inheritance**, and wired into the skills/rules **enable/disable/lock** control system.

## What exists today (grounded)

Standards are already a two-tier, OpenCode-native rule system:

- **`.cursor/rules/*.mdc`** — thin, agent-facing rule *pointers*. Frontmatter OpenCode honors natively:
  ```
  description: Module layout + public/internal — pointer to standards SSOT
  globs: "{src,packages/last-ts/src,examples,test}/**/*.{ts,tsx}"
  alwaysApply: false
  ```
  Body = a tight summary + a link to the SSOT. Current set: `no-casts`, `no-shims`, `no-waku-app-imports`, `module-layout`, `effect-style`.
- **`docs/standards/*.md`** — the full authoritative standard documents.
- **`docs/standards/manifest.json`** — the catalog, generated by `docs/site/scripts/gen-manifest.ts` from `{#id .severity appliesTo}` blocks. Top-level: `chapters`, `ruleCount`, `generated`. Per rule: **id**, **severity**, **appliesTo**. CI-freshness-checked (`pnpm docs:manifest:check`).
- **App today:** repo menu = `Files · Docs · Commits · Pull Requests`; workspace = `Files · Docs` (`repoMenu.ts`, placeholders, not wired). Docs itself not built yet.
- **Web reader (to mirror):** grouped nav/sidebar, code + copy, glossary hovers, prev/next, page meta, edit-this-page, search, API-symbol rendering, precomputed twoslash hovers (`docs/site/src/components`, `.../islands`).

The manifest already encodes exactly what the app needs: **id** (→ control-channel reference), **severity** (→ enforce/lock tier), **appliesTo** (→ applicability mode), **chapters** (→ nav grouping). So the app's Rules catalog is **manifest-canonical**.

## Navigation & surface

- Add **Rules** to `REPO_MENU` and `WORKSPACE_MENU` immediately **below Docs** (`repoMenu.ts`). Icon candidate: `checklist` / `ruler` / `seal`.
- **Rules screen** = a catalog driven by `manifest.json`, grouped by **chapter** (like the docs sidebar). Each row: name + description, a **severity badge** (→ enforced/lock), an **applicability tag** (always / when-editing-`<glob>` / on-request), and its **enable/lock** state. Tapping a rule opens it in the shared reader.

## Shared reader (Docs === Rules)

One markdown reader powers **Docs, Rules, and a rule's full standard doc**. Feature parity with the web, phased:

- **P1:** markdown render, on-device Shiki code blocks + copy, cross-doc links, prev/next, page meta, chapter sidebar.
- **Later:** search across docs+rules, glossary hovers, twoslash/precomputed hovers (parity with the web islands).

A rule opens showing its `.mdc` (summary + frontmatter surfaced as metadata: severity, appliesTo, mode) with a clear affordance to open the **full standard** (`docs/standards/*.md`) — the two-tier progressive disclosure the standards already use (light pointer always/glob-applied; full doc loaded on demand, skill-style).

## Data model & inheritance

- **A "rule" in the app** = the `.mdc` (frontmatter `id`/`description`/`globs`/`alwaysApply`, plus manifest `severity`/`appliesTo`) + its linked SSOT `docs/standards/*.md`. Manifest is the catalog SSOT.
- **Inheritance: root → repo → folder** — mirrors OpenCode's own `globUp` (it walks the directory tree collecting instruction files). Root rules apply to every repo; a repo adds/overrides; a folder/worktree adds further. **Repo/folder rules inherit top-level rules.** Locks flow **downward**: a rule locked at root can't be overridden by a repo or session; locked at repo can't be overridden by a session.

## Editing

- Editable at **both tiers**: the rule `.mdc` (pointer body + frontmatter) **and** the full SSOT `docs/standards/*.md`.
- Frontmatter (`severity`, `appliesTo`/`globs`, `alwaysApply`, `id`) edited via a **structured form**, not raw YAML, where practical.
- File ops go through the off-vite Effect server (same pattern as extensions/fonts/skills), committed into the repo. After an edit, **regenerate the manifest** (`gen-manifest`) so the catalog stays fresh; the existing CI check guards drift.
- Editor surface: reuse the Monaco code surface once it lands (`agent-console-code-surface-phase0.md`); interim, a lighter markdown editor. Read-only first, editing as a later phase.

## AI-assisted rule update (NEEDS DISCUSSION — documented, not specced)

The **primary** editing affordance the owner wants: update a rule with AI. Candidate flows to design later:
- **Rewrite/tighten** a rule from a natural-language ask (edits `.mdc` + SSOT).
- **Sync the tiers** — regenerate the `.mdc` pointer from the SSOT (or vice-versa) so the summary and full doc never drift.
- **Draft from evidence** — turn a code pattern, a review finding, or a diff into a new rule (id/severity/appliesTo inferred).
- **Suggest frontmatter** — propose `severity`/`appliesTo` for a hand-written rule.

Open questions (defer): which agent/model runs it; how edits are previewed/approved (diff gate); manifest-regen coupling; and self-enforcement — the AI editing standards must itself obey the standards. **Do not build until discussed.**

## Tie-in to the skills/rules control system

From the prior discussion (skills doc pending), rules participate in the shared, app-managed **per-turn `<system-reminder>` control channel**:
- **Enforced** rules (manifest `severity` at the strict end, e.g. `no-casts`) → **locked at repo/root**; a session cannot suspend them.
- **Softer** rules → session-suspendable via the control channel.
- Rules are hard-always-on by default (OpenCode caches config per session); the control channel adds an **opt-in soft-suspend**, and **locking = withholding that opt-in at/above a scope**.
- The Rules screen's enable/lock toggles drive this control state; the reader/editor manage content. (Full mechanism lives in the forthcoming skills-management doc; keep the two consistent.)

## Feature-parity checklist (web → app)

Rendering · code highlight + copy · chapter/grouped nav · prev/next · page meta · edit-this-page (→ our editing) · search · glossary hovers (later) · twoslash/precomputed hovers (later) · manifest catalog · severity + appliesTo surfacing.

## Phasing

1. **Catalog + reader (read-only).** Rules menu item; manifest-driven catalog grouped by chapter; shared reader shows the `.mdc` + full SSOT; applicability + severity surfaced.
2. **Control wiring + inheritance.** Enable/disable/lock via the control channel; root→repo→folder inheritance and downward locks.
3. **Editing.** Edit `.mdc` + SSOT via the off-vite server; structured frontmatter form; manifest regen.
4. **AI-assisted update.** After the design discussion above.
5. **Cross-cutting later.** Search, glossary/twoslash hovers — full web parity.
